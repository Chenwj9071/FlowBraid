# FlowBraid 开发经验与避坑指南

本文归档本次会话中暴露出来的典型问题，重点覆盖三类：
- 方案设计缺陷
- 开发过程错误
- 编码和终端显示问题

目标不是复盘情绪，而是沉淀可复用的操作规范，避免同类问题再次发生。

## 1. 方案设计层的坑

### 1.1 不要把“输出看起来正常”当成“状态机真的正确”
本次 native split 和 approval 相关问题，表面上是日志粘连、游标错乱、旧日志被覆盖，实际上背后有两类更深的问题：
- 主进程和子终端都在写输出，但没有明确的输出边界
- 节点状态、attempt 状态、终端会话状态混在一起，导致回流和收尾阶段容易串线

经验：
- 只看终端现象不够，必须回到状态文件、事件文件和会话文件验证
- 对会流转的节点，必须显式区分 node、attempt、session 三层身份

### 1.2 不能用“共享目录推断会话”
native split 里如果只按 `workdir` 或最近文件去推断当前 session，很容易误恢复别的节点会话。

经验：
- 恢复必须绑定节点自己的 sessionId
- 共享目录只能承载业务文件，不能当作会话索引

### 1.3 outcome / verdict / approval 语义要分开
这次一度出现“review verdict 还在用，outcome 又已经引入”的混搭状态，容易让调度逻辑、文档和示例各说各话。

经验：
- 一个阶段只保留一个真源状态
- 兼容层要明确标注，不能让作者猜哪个字段生效

## 2. 开发过程层的坑

### 2.1 不要先信终端显示，再去改代码
这次最典型的问题就是：终端显示乱码、文件看起来像坏了、输出好像被覆盖，但真实原因可能是：
- 控制台编码不一致
- PowerShell 默认编码和文件编码不一致
- 写文件时经过了错误编码链路

经验：
- 先验证字节内容，再看终端显示
- `Get-Content`、命令行输出、文件内容三者不要混为一谈

### 2.2 修复要从“最小可证伪假设”开始
当一个修复“看起来合理”但验证后现象完全不变，通常是方向错了，不是力度不够。

经验：
- 先构造最小样例，再定位问题
- 一次只改一个变量
- 每次修改都要有可观察的验证点

### 2.3 文档修复要用“可逆、分段、可验证”的方式
本次文档乱码修复里，最容易犯的错误是：
- 直接重写整份文档
- 不区分“内容损坏”和“显示损坏”
- 通过终端编码链路去写 UTF-8 文件

经验：
- 先确认文件真实编码，再决定是转码还是重写
- 文档修复优先保留语义，不要顺手改成“顺眼但不准”的新版本
- 写完后必须用字节级方式复核

### 2.4 失败修复要尽早停手
当连续几轮修复结果都没有改变现象时，说明当前路径大概率不对。

经验：
- 不要在错误假设上继续叠加补丁
- 先暂停，重新做证据链确认
- 必要时回到设计层重新定义边界

## 3. 编码和终端层的坑

### 3.1 Windows 下的“乱码”经常不是文件坏了
本次出现过两种不同问题：
- 文件内容本身确实被写坏了
- 文件内容正确，但终端输出用错编码，显示成乱码

经验：
- 文件编码、终端编码、编辑器编码要分别确认
- 不要仅凭终端截图判断文件是否损坏

### 3.2 UTF-8 写入要避免经过控制台中转
通过 shell、Python、PowerShell 交叉传递中文内容时，如果中间任何一步用了错误编码，就可能把中文写坏。

经验：
- 写文件时优先走直接文件 API
- 避免把大量中文正文塞进命令行参数
- Windows 上编辑中文文档时，优先用明确的 UTF-8 写入路径

### 3.3 验证要用“读回原字节”的方式
最可靠的检查方式不是看终端，而是：
- 读文件 bytes
- 直接用 UTF-8 解码
- 检查是否存在 `\uFFFD` 或异常替换符

## 4. 可复用操作流程

遇到类似问题时，建议按这个顺序处理：
1. 先把现象拆成“设计问题 / 实现问题 / 编码问题”
2. 先验证文件和状态，不先动代码
3. 先做最小样例，再扩大范围
4. 只改一个假设，改完立即验证
5. 终端显示和文件字节分开判断
6. 修完后补一条能长期约束后续开发的文档

## 5. 精简规范

下面这几条可以直接当日常开发规范：

1. 先验字节，再看终端。  
2. 先定边界，再改代码。  
3. 共享目录只放业务文件，不放会话真源。  
4. 一个节点只保留一个真状态源。  
5. 修复必须可验证，不能靠“看起来好了”。  
6. 失败两轮还没变，就先停下来重建假设。
